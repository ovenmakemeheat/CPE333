# บทพูดภาษาไทย (ร่างแรก)

แต่ละหัวข้อ `##` คือฉากหนึ่งในวิดีโอ แต่ละบรรทัด `-` คือซับไตเติลหนึ่งบรรทัด
เวลาที่แสดงคำนวณจากความยาวข้อความ (ประมาณ 12 ตัวอักษรต่อวินาที ไม่นับสระบน-ล่างและวรรณยุกต์)
ถ้าเสียงจริงพูดเร็วหรือช้ากว่านี้ ให้แก้ `TH_CPS` ใน story_scene.py แล้ว render ใหม่
แก้ข้อความได้เลย บรรทัดยาวจะถูกตัดเป็นสองบรรทัดเองตรงช่องว่าง

## opening
- สวัสดีครับ พวกเราคือกลุ่ม Ta Nai Tum Chuoy Soo
- วันนี้จะพาไปดูว่า หน่วยความจำของโปรแกรมหนึ่งตัว จริง ๆ แล้วไปอยู่ที่ไหน
- เวลาที่โปรแกรมเรียกใช้คำสั่งจองพื้นที่ mmap หรือ brk มันแค่จองแค่ช่วง address
- โดยไม่ได้เข้าถึง RAM page จริงๆ เลย
- Linux จะให้ physical page นี้ตอนที่ถูกโปรแกรมเข้าถึงครั้งแรก
- และมันคือจังหวะแรกที่ CPU จะเด้งเข้าไปใน kernel ที่เรียกว่า page fault
- มันก็จะ fault ไปทีละหน้า ตามลำดับที่ถูกใช้

## analogies
- เครื่องมือของเราให้ตัวเลขสี่ตัว สำหรับ process เดียว
- จำนวน region, ขนาด address space และ minor กับ major fault

## goal
- บล็อกที่เห็นคือ address space ของ sleep
- หนึ่งบล็อกคือหนึ่ง region
-  แต่ละสีบอกว่ามาจากไฟล์ที่เป็น anonymous หรือเป็น heap กับ stack

## background
- บล็อก 1 บล็อก คือ VMA หนึ่งตัว
- มันคือช่วง address ที่ต่อกันตั้งแต่ vm_start ไปจนถึง vm_end
- ข้างในมี page ซึ่งตอนนี้ทุก page ยังว่าง
- พอโปรแกรมเรียกใช้ ก็จะไปต่อที่ kernel
- kernel เติม page นั้นให้ แล้วส่งกลับมาให้โปรแกรมทำงานต่อ
- ทีนี้ kernel จะไปดูใน page cache ก่อน ว่ามีของอยู่ใน RAM อยู่แล้วไหม
- ถ้าเจอ ก็ map ให้เลย เร็วมาก แบบนี้เรียกว่า minor fault
- ถ้าไม่เจอ ต้องไปอ่านจาก disk ก่อน โปรแกรมต้องรอ อันนี้คือ major fault
- ต่างกันแค่ไหน ประมาณหนึ่งไมโครวินาที กับหนึ่งมิลลิวินาที
- ช้ากว่ากันราวพันเท่าเลย
- ส่วนการตัดสินว่า fault ไหนเป็น major เราใช้กฎเดียวกับ kernel ใน mm_account_fault
- ถ้าเป็น retry ยังไม่นับ ให้รอต่อไป
- ถ้า error ก็ไม่นับ ถือว่าเป็น fault ปกติ
- ถ้ามีการอ่าน I/O (disk) หรือเคย retry มาแล้วถึงจะ นับเป็น major

## regions_walk
- เริ่มจากรัน pfstat ใส่ PID ของ sleep
- ฝั่ง kernel เราขอ mm ของ process นั้นมาก่อน
- แล้วล็อกไว้แบบอ่าน กันไม่ให้ map เปลี่ยนระหว่างที่เราเดินดู
- จากนั้นวน for_each_vma ทีละ region
- เจอหนึ่งตัวก็นับเพิ่ม แล้วบวกขนาด vm_end ลบ vm_start
- จากมุมนี้ จะเห็นเลยว่า mapping ของไฟล์ตัวใหญ่ตัวเดียว กินพื้นที่เกือบทั้งหมด
- สุดท้ายได้ 30 region กับ 5.6 MB ตรงกับที่ Linux รายงานก่อนหน้านี้เป๊ะ ๆ เลย

## fault_counting
- ทีนี้มานับ fault กัน เราวาง kretprobe ไว้ที่ handle_mm_fault
- probe ตัวนี้จะเห็นทุก fault ในเครื่อง ของโปรแกรมอื่นเราปล่อยผ่านไป
- ส่วนของ process เป้าหมาย เราเก็บไว้ แล้วรอดูผลตอน return
- พอรู้ผลแล้วก็แยกเป็น minor หรือ major และเป็น anon หรือ file
- อย่างตัวนี้ที่แตะ 64 MiB ได้ 16,538 minor กับ 1 major
- ตรงกับ getrusage ที่รันก่อนหน้านี้ทุกตัว
- ในกรณีที่โปรแกรมมีเวลาสั้นมาก ๆ
- เราก็มี probe ตอน exit ไว้ เก็บจำนวน region กับขนาดไว้ก่อน mm จะหายไป

## demo
- มาดูของจริงกัน รัน pfstat แบบ run mode ให้มันสั่ง faultgen เอง
- ลูกจะหยุดตัวเองด้วย SIGSTOP ให้เราอ่าน baseline ได้ 468 fault
- แล้วค่อยปล่อยด้วย SIGCONT ให้ exec โปรแกรมจริง
- faultgen map 64 MB address space โตทันที แต่ RAM ยังไม่ขยับ
- พอแตะทุกหน้า minor fault ก็วิ่งขึ้น หน้าละหนึ่งครั้ง
- ต่อด้วยอ่านไฟล์ 32 MB ที่ไม่อยู่ใน cache ทุกหน้าต้องไป disk
- ได้ major fault 8,193 ครั้ง
- พอ free ทุกอย่างกลับมาที่ 16 region
- และตัวเลข 16,521 กับ 8,193 ตรงกับ getrusage หลังหัก baseline

## experiments
- ต่อไปคือการทดลอง สภาพแวดล้อมคือ Ubuntu 24.04 บน Linux 6.8 ARM64
- ไฟล์ 32 MiB เดียวกัน อ่านแบบสุ่มตอน cache เย็น ทุกหน้าเป็น major
- ถ้าอ่านเรียงกัน readahead ดึงล่วงหน้าให้ เหลือ major แค่ 2
- ถ้าไฟล์อยู่ใน cache แล้ว fault หนึ่งครั้ง map ข้างเคียงได้ 16 หน้า
- ส่วน THP ใช้หน้าใหญ่ 2 MB เหลือแค่ 188 minor จาก 16,538
- สรุปคือ จำนวน fault ไม่ได้ขึ้นกับขนาดไฟล์อย่างเดียว
- แต่ขึ้นกับ cache readahead fault-around และ huge page ด้วย

## checks
- ทีนี้มาเช็กความถูกต้อง ฝั่งซ้ายคือ pfstat ฝั่งขวาคือ /proc ของ Linux
- ทั้ง sleep และ PID 1 ตรงกันทุกตัวเลข ทั้ง region ขนาด minor และ major
- ต่อมา ทำไมไม่ใช้ tracepoint ที่โจทย์แนะนำ
- เพราะมันมีแค่บน x86 แต่ VM ของเราเป็น ARM64
- แล้วมันยิงตอนเข้า fault ยังไม่รู้เลยว่าจะเป็น minor หรือ major
- kretprobe ยิงตอน return เห็นผลจริง และใช้ได้ทุก architecture
- หลัง merge เรารัน regression อีกรอบ บน kernel 6.8.0-147
- ลองสลับ target กลาง fault ดู fault ที่เริ่มกับ A ก็ยังลง session ของ A
- ไม่หลุดไปนับให้ B
- รวมแล้วหกเคส PID reuse thread exit พร้อมกัน อ่านสองหมื่นครั้ง ผ่านหมด
- E8 ลองกับ sh ที่รัน ls ถ้านับแค่ตัวเอง ได้ 258 ขาดไป 135
- เปิด -f ให้นับลูกด้วย ได้ 390 ตรงกับ wait4
- gcc ก็เหมือนกัน นับแค่ gcc ได้ 287 ขาดไปตั้ง 5,700
- เพราะงานจริงอยู่ที่ลูกของมัน cc1 as collect2 และ ld
- และ wait4 รวม fault ของลูกที่รอไว้ให้แล้ว
- เปิด -f ได้ 5,971 ตรงกับ wait4 ในรันนั้น
